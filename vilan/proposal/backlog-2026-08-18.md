25. **NEW — remote sources: subscribe by demand, unsubscribe at zero** (M; owner's 2026-08-18 playground notes, item 1)
    STATUS: OPEN (proposal-first — a short paper; the owner's design sketch is the brief)
    Today `RemoteSource<T>` (std/src/rpc.vl ~1251) has `get(): Option<T>`
    and `sub(observer)`, and `sub` flips a `wanted` flag and sends
    `Subscribe` — **nothing ever sends `Unsubscribe`**: disposing the
    returned `Subscription` stops the observer, not the channel, so a
    mirror once watched stays on the wire for the session ("I don't want
    exposed signals to auto-subscribe and carelessly waste network when
    it's not even needed" — the owner). And because `RemoteSource` is not
    a `Source<T>` (its `get` is `Option<T>`), the todo client mirrors it
    by hand into a local `Signal` (`client.vl:15,21` — `Signal::new([])`
    + a `_sync` subscription held forever) before `bind_each` can use it.
    The owner's sketch (from kolt's design under SolidJS's `getListener`
    owner): a mirror captured under a reactive scope subscribes if not
    already and increments a count; cleanup decrements; zero unsubscribes
    from the server automatically — and since vilan is explicit rather
    than scope-based, hang the same logic on `.map` (and on embedding,
    `<p>{RemoteSource}</p>`): a subscription lives until disposed and the
    count reaches zero. Open question the owner raised: is `RemoteSource`
    a `Source` implementor, or a bespoke interface through which a
    source/signal is reached? Orchestrator's recommendation, for the
    paper to argue: (1) the count rides `Subscription` disposal, which
    reactive-ownership.md already ties to the owning view/scope — so an
    unmount decrements without a `getListener`; `rebind` re-subscribes
    iff count > 0; (2) keep `RemoteSource` bespoke (`get(): Option<T>` is
    honest before the first `Update`) and add ONE seam that yields a real
    `Source<T>` — `.or(initial: T)` (reads `initial` until the first
    frame; refcounted while anything listens) — so `.map`, `bind_each`
    and embedding all inherit through `Source` with no new machinery, and
    the `Option` is confronted exactly once, where the todo app already
    supplies `[]`; optionally `.ready(): Task<Source<T>>` for the
    await-first-value shape. **Owner refinement, 2026-08-18:** the
    direction is accepted "as long as there's a way to use a fallback
    system instead of having to set an initial" — the case: a counter
    showing "Loading..." until the count arrives, a fallback of a
    DIFFERENT type than T. So the paper must give: `.map<U>(|Option<T>|
    U): Signal<U>` (counted — observing the arrival IS a subscription,
    released with the owner) as the fallback tool; `.or(initial: T)` as
    sugar over it; and a **passive** `status(): Source<Status>` (the
    owner prefers "status" over "state" — SolidJS's `Resource.state`
    is the reference) reading local knowledge only (Waiting / Ready /
    Stale-on-transport-loss) without opening the channel — for the
    developer who wants to know without wanting the value; `get()` stays
    the passive snapshot. The honest sentence the paper states: any path
    that renders the value when it arrives subscribes; the count is what
    makes that harmless. Paper: transport-rpc.md's successor section or
    a small `remote-sources.md`; the generated client keeps
    `RemoteSource` fields.

4. **`const_eval::evaluate` is two thirds of a style-heavy compile** (M; found by M1's baseline)
   STATUS: OPEN (part SHIPPED 2026-08-18 — the local hoists, const-eval.md §10.1–10.4; §10.5 RULED 2026-08-18: Option A as recommended — one shared const world per analysis; scheduled next order as M4-A)
   Profiled 2026-08-18 (const-eval.md §10). The pass is **linear** in const
   sites at a flat ~0.75 ms/site release; the website's gap over kolt is site
   count times chain length — 483 evaluations against at most 18 — and nothing
   degrades with scale, so the
   filing's super-linear suspect was wrong except for one 3.4 % term
   (`in_const_subtree`'s O(sites × call sites) span scan). Two thirds of the
   per-site cost is the interpreter computing the style itself (0.094 ms per
   property, zero intercept — irreducible within one analysis); one sixth was
   a per-site rebuild of program-wide state, chiefly a 4,184-entry source-name
   map built once **per const site**. Those hoists SHIPPED: const_eval on the
   website is 3408 → 2799 ms debug and 429 → 308 ms release, `vilan check`
   −12.7 %, and `page.vl`'s keystroke p50 321.5 → 252.4 ms (still 1.68× the
   150 ms debounce, was 2.14×). Byte-identical output; three pins. **Live
   remainder**: §10.5's two options — (A) one shared const world per analysis,
   recommended, ~25–30 % of what is left; (B) cross-analysis memoization,

   as M4-A; B stays deferred behind §8.3's cache-key question.
   History: the const pass cost **4.21 s of the website's 6.60 s `vilan check`**
   — 64% of the wall, and 89% of everything `post_analysis_passes` does

   debug profile, 2026-08-18; perf-baseline.md §4). It is not
   proportional to source size: kolt is a third of the website's lines
