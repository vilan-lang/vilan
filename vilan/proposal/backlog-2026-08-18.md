78. **NEW — the unprovided-context error underlines the whole call chain, not just its anchor** (M; owner's 2026-08-20 ask)
    STATUS: OPEN
    The owner, verbatim in spirit: every function call UPSTREAM of a
    `context.get()` with no provider should carry an error span — the
    auxiliary spans are what make the error legible, because today
    "calling a function could 'randomly' make an error appear somewhere
    else entirely"; having each call on the path underlined and pointing
    toward the source is a huge DX win, and rust-analyzer is the prior
    art (its trait-bound/requirement chains render as related spans at
    every hop). The infrastructure is three-quarters built: E74's
    `user_entry_of` walk (context.rs) already TRAVERSES the exact chain
    — direct calls, dispatch-narrowed calls, top-level entries, capture
    hops, through unbound callers — and then keeps only the least-id
    endpoint as the anchor plus ONE std note. This item keeps the whole
    path: the primary stays at E74's anchor, and every intermediate call
    frame between the anchor and the strict read gets its own labeled
    span ("the context requirement flows through this call"), ordered
    entry → read, rendered as ariadne labels in the CLI (multi-label
    already exists — the Note machinery) and as
    DiagnosticRelatedInformation in the LSP so editors underline each
    hop. Design points for the lane: one chain or all chains when
    several uncovered entries reach the read (E74 picks least-id — the
    others likely deserve their own primaries anyway, they get their own
    walks); a length cap with an honest "… N more frames" tail; the
    label wording enters the diagnostics ledger (heads are keys); the
    dispatch hops inherit E74's union-admission residual and should say
    so in the label rather than overclaim. Applies identically to the
    `owner_scope` coverage flavor (the same walk serves both). Record:
    E74's machinery (context.rs, async-polymorphism.md §A.4b); the
    ledger rows 222/223.
